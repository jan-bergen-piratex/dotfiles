# Handoff Creator

Use this skill to create a pickup document that lets a person or agent continue
work without rediscovering context.

## Required Header

Every handoff must include these fields near the top:

```text
from:
to:
date:
time:
```

Rules:
- `date` must be an exact date in `YYYY-MM-DD`.
- `time` must include timezone when known, for example `10:45 Europe/Berlin`.
- If a field is unknown, write `unknown` and explain the source of uncertainty.
- If the handoff is generated by Codex for Jan to send onward, use
  `from: Jan / Codex-assisted` unless Jan specifies a different sender.
- If the handoff is for a future agent, name the target explicitly, for example
  `to: incoming Codex session`, `to: Mary setup Codex session`, or
  `to: Manuel`.

## Placement

Do not scatter handoffs.

Choose the narrowest durable home:
- Project repo handoff for active engineering work: project-local docs/backlog/handoff area if one already exists.
- Jan personal pickup or cross-repo handoff: `/home/jan/pirate/notes/prompt_files/` only if it is a prompt, otherwise ask before writing to notes.
- Tech-brain/Mary/Hermes architecture handoff: `tech-brain` only when Jan clearly asks or the work already lives there.
- Piratex-brain knowledge handoff: `piratex-brain/00_Inbox/` only when it is genuinely company-brain intake; otherwise do not put operational tasks there.
- Temporary Codex-only memory: `/home/jan/.codex/codex-notes`.

If the target location is unclear and writing to a shared repo would matter,
ask Jan or draft in `/home/jan/.codex/codex-notes` and say it has not been
promoted.

## Content Contract

A useful handoff should answer:
- What project or system is this about?
- What changed?
- What is currently true?
- What was decided, and by whom?
- What remains open?
- What is blocked, and on whom?
- What files, commands, URLs, branches, commits, services, credentials, or docs matter?
- What should the receiver read first?
- What should the receiver do next?
- What must not be changed or re-litigated without discussion?

Keep it concise enough to be read in one pass. Do not turn the handoff into a
full project archive unless Jan asks for that.

## Evidence Rules

Before writing a handoff:
1. Read the current repo status and recent commits when the handoff is about a repo.
2. Read existing project docs, backlogs, or prior handoffs to avoid duplicates.
3. Separate verified state from assumptions.
4. Include exact paths for important files.
5. Include command results only as short summaries; do not paste long logs.

Use labels when helpful:
- `verified`
- `assumption`
- `open`
- `blocked`
- `do not change`

## Open Work Format

For open items, prefer compact actionable entries:

```text
- Task:
  Owner:
  Source:
  Blocker:
  Next action:
```

Use a lighter bullet list if there are only one or two open items.

## Update Existing Or Create New

If an existing current handoff already covers the same project:
- update or append only when Jan asked to write into that location.
- otherwise produce a proposed replacement/append in chat or in Codex notes.

If the existing handoff is stale:
- say what supersedes it.
- create the new one with a date-specific filename.
- do not delete the old one unless Jan explicitly asks for cleanup.

## Validation

Before finalizing:
- Verify the handoff contains `from`, `to`, `date`, and `time`.
- Re-read the written file.
- Check that referenced local paths exist when practical.
- If it is in a git repo, report `git status --short` for the touched file.

Final response should name the path, the intended receiver, and any uncertainty
that remains.
